# `src/main/diagnostics/`: why the code has its shape

This holds why the code here has the shape it has, and is read only when changing a decision made here. [`README.md`](README.md) is the map.

**A run the window system ended is `display-lost`, not an abnormal exit.** On Linux under Wayland the desktop can drop a client that stalled, and Chromium cannot go on without its display connection: the shell window is destroyed with no `close` event (only `closed`) and the process ends without `before-quit` or `will-quit`, so the run marker stays behind and the next start would call it "ended without an orderly quit", which a person reads as Orivon crashing. The shell calls `noteWindowSystemEnd` from the window's `closed` handler when `close` never ran; it writes `endedBy: 'window-system'` and the stall counts at that moment into the run marker before it returns, since nothing runs after it, and logs one line. The next start's `uncleanExitRecord` then gives the record the reason `display-lost` and words that say the desktop's display server ended its connection. The kind stays `unclean-exit`: the report server accepts only the four kinds of `CrashKind`, and `reason` is free text. Three runs are left alone: one that recorded a fatal error (`app.exit()` destroys windows without a close too, and that run has its own record), one that quit in order (the marker is gone and a closing window must not bring it back), and one a native dump explains (the dump says what happened; the marker field is only the cause when nothing crashed). The stalls go in the marker, not only in the report's `browser.mainStalls`, because a report is built by the next run, whose counts are its own.

**The main process's stalls are read from a timer's lateness, not from `monitorEventLoopDelay`.** `main-stalls.ts` runs a 500 ms timer and reads how late each run is. A `monitorEventLoopDelay` histogram holds percentiles over a window: it cannot say how many stalls passed 1 s or 5 s, nor when each one was, and both are what the report's counts and the one log line per stall of 2 s or more need. The price is that a stall reads up to one interval short. The clock is `performance.now()`, which does not move with the wall clock; a delay of ten minutes or more is the computer asleep and is not counted. A stall line is limited to six a minute so a main process that keeps stalling cannot push the log's 1000 lines out; the counts still hold every stall. The six is *provisional*; a real log would settle it.

**The Nym tunnel's host writes only its own lines to the log.** The WebAssembly library the host runs passes its own strings to
`console.error` and `console.warn`, and they can name where a Nym-routed app connects, which is what Nym exists to hide. Every line
the host's own code writes begins with `[nym-tunnel]`, its unhandled-rejection handler included; `HostLog`'s `onlyTagged` counts
the others and leaves them out, and one line a minute says how many came "from the Nym library". What Node prints itself when the
host crashes carries no tag and is left out as well: the supervisor reports the exit and its code. This is a `HostLog` option, not
Nym code here, so another host that runs a library can ask for it.
