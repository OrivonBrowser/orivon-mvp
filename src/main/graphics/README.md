# `src/main/graphics/`: WebGPU on an X11 session

**What lives here.** The opt-in setting `graphics.webgpuOnX11` and what it does to this process: whether it
applies, the switches it sets before Chromium reads them, the guard that turns it off after a bad run, and what Settings
may ask about it.

**What it depends on.** `electron` (`x11-vulkan-runner.ts` only); [`../settings/`](../settings/) (`readSettingBeforeReady`, `forceSettingsFile`, the store's `set` and `onChange`); [`../privacy/gpc-switch.ts`](../privacy/gpc-switch.ts) (the merge of one feature into `--enable-features`); [`../diagnostics/shell-console.ts`](../diagnostics/shell-console.ts) (`isOrdinaryEnd`, so the guard and the crash records agree on what a bad end is); [`../pages/internal-ipc.ts`](../pages/internal-ipc.ts) (the shape of a domain); [`../../broker/adapters/atomic-write.ts`](../../broker/adapters/atomic-write.ts) (the guard's record lands whole or not at all).

**What it must never import.** [`../shell/`](../shell/) or the renderer: `index.ts` hands it the settings store and the publisher once they exist, and tells it when the first window was shown and when it painted.

**Owner stream.** `shell`.

**Electron dependence.** Pure: `x11-vulkan.ts` (the rules and the guard's decisions), `guard-file.ts` (plain `fs`) and `graphics-domain.ts`. Tied to Electron: `x11-vulkan-runner.ts`.

## Design notes

**The switches are `--use-angle=vulkan` and `Vulkan,VulkanFromANGLE`, because that is the smallest set that kept everything working.** Chromium 152 gives a page no WebGPU adapter on X11 for any graphics card (it sets the bridge from GL to Vulkan only under Ozone Wayland). With these switches the page gets an adapter and WebGL, painting and both VP9 and H.264 video still work, on a standalone Xwayland and under xvfb. Without `VulkanFromANGLE` WebGL is lost; without `Vulkan` there is no adapter. The set is added to `--enable-features` the way [`../privacy/gpc-switch.ts`](../privacy/gpc-switch.ts) adds its feature: Playwright's Electron launcher replaces a feature list given on the command line, so a test can reach the setting only through the profile's `settings.json`.

**It acts only where Orivon already runs on an X11 session, and never forces it.** Settings offers the choice and the switches apply by one rule, `offersX11Setting`: Ozone X11 on a session that is not Wayland. `ozonePlatformOf` is the one answer to "which Ozone platform", for the guard, the About page and a report. It mirrors what Electron 44 does before any script runs (`SetOzonePlatformForLinuxIfNeeded`, called from `ElectronMainDelegate`): an `--ozone-platform` switch that is set wins, else Wayland when `XDG_SESSION_TYPE` is `wayland`, else X11. `WAYLAND_DISPLAY` is not read; it belongs to `--ozone-platform-hint=auto`, which Electron does not use. Forcing `ozone-platform: x11` on a Wayland session crashes the graphics process on some computers (`../README.md`), so this setting is never a way to get X11. Orivon running on X11 inside a Wayland session (XWayland) is told to run on Wayland instead: neither the row nor the switches reach it, and a profile that has the setting on keeps it unapplied there.

**Which card Vulkan picks is not the setting's to say.** On a laptop with two graphics cards the Vulkan device is the NVIDIA one whatever render node Chromium was given; Intel is reached only by limiting Vulkan to its driver with `VK_ICD_FILENAMES`, which is no Chromium switch. The help text says what this costs.

**The guard exists because the reason Chromium turned this off is a blank video on some laptops, and a crash is the other way it can go wrong.** It reverts in three cases, and keeps which (`gpu-crash`, `gpu-software`, `no-window` in `x11-vulkan.json`, carried in a report). Settings and `orivon://gpu` say one thing for all three: Orivon turned it off because graphics stopped working while it was on.
- the graphics process ended badly in a run that set the switches (the same ends the crash records count, `isOrdinaryEnd`), except while Orivon quits or starts again, when every process ends: the setting is turned off at once, and takes effect at the next start;
- ten seconds after the first window is shown, and again whenever Chromium updates its graphics report (`gpu-info-update`), Chromium draws pages on the processor (`app.getGPUFeatureStatus().gpu_compositing` is not `enabled`): a Vulkan driver that cannot be loaded makes the graphics process exit during its start-up and start again until Chromium gives up, which no end of a process reports. The setting then gave nothing and cost every page its graphics card, so it is turned off. On a computer that drew on the processor before the setting was on, the guard turns it off too, on purpose;
- a run that set the switches never painted its first window: the start marker is written before Chromium reads the switches and removed when the window's `ready-to-show` comes, never by the timer that shows the window a second after its creation whether or not anything was drawn, so the next start finds it and reverts before applying anything. Orivon's own ends of a start (the failed-to-start dialog, an uncaught error) clear the marker, because they are not the switches' doing; a start killed from outside leaves it. A run from the development server may never get `ready-to-show` (`../shell/window-frame.ts`), so its marker stays and the next start with the setting on turns it off.

A setting that reads on beside a revert in the record at start is a turn-off the settings store had not saved yet (it saves after a delay): the switches stay off, the setting is turned off again and the record stays. Turning the setting on from Settings forgets the record at once. In a private window the switch is locked, so no sentence sends the person to it. A private session follows the copy of the settings it started from and keeps its own record, which goes with it.

**Not measured.** A real Xorg session, which is the case upstream's block was written for (video composited blank on an NVIDIA hybrid laptop). Until a computer like that has run this, whether the video decoder picks the integrated GPU there is *provisional*; a report from `orivon://report` on such a computer would settle it.
