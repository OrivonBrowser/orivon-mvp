# `src/protocols/verifier-host/light-client/`: design

The rationale behind [`README.md`](README.md)'s notes on the execution servers.

**A slow execution server is hedged after 1 s, one that hangs is given up on after 10 s, and one that failed is asked last.** `rpc-failover.ts` runs each request through `racePass`: the first server is asked, the next is asked too when the first has not answered within 1 s (never more than two at a time), the first good answer wins and the others are cancelled, and a server that fails at once is passed over at once. A server is given up on 10 s after it was asked, headers and body, and its fetch is aborted, but only while another server is still to be asked in its place; the last servers asked are waited on, bounded by Helios's request signal and the 45 s a mount waits. One cap from the moment of asking covers headers and body, since an answer is a small JSON document (the gateways' stall clock is for large transfers). Helios's `eth_call` waits on every request it sends and Electron's `net.fetch` has no timeout, so one `eth_getProof` held by a server would hold the name's proof until that server gave up, past the 45 s a mount waits. This is safe because Helios checks every answer against its proofs, whichever server sent it. Each server keeps a `GatewayHealth` for as long as its failover lives (`light-client.ts` replaces the failover only when the servers in use change): a second timeout in a row, a connection that could not be made, a rate limit or a server error sets it aside for seconds, growing with repeats, and a request asks the servers not set aside first, then the others, each in the order given (none is dropped, since all may be set aside). A server outrun before it sent its headers counts as a timeout; one outrun after it began to answer counts as nothing; a JSON-RPC error, which is what a short proof window answers, is no fault. A pass that ends with no usable answer, after a server failed in a way it may not repeat (an error answer, a rate limit, a server error), is followed by one more after 0.3 s; one of only unreachable or silent servers is not. A hedged request reaches a second operator from the same configured list, which otherwise saw it only when the first failed; keeping a slow server at the back makes hedges rare. `../pace.ts` gives both waits, stretched for a tunnel by how much slower it is; the client sends these requests only once it has synced over that route, so they carry no allowance for a tunnel still coming up. The log says once, when a server is set aside, which one and why, address masked (`an execution server (<address>) did not answer in time; the others are asked first for 2 s`), and a mount that runs out of time says whether it was waiting for a slot, proving the name or loading its content, without the name (`serve/sites.ts`). The two figures are provisional: the hedge rates and latencies of execution servers measured in bug reports would settle them.

**`serverReads` is the light client's own servers asked for what it cannot prove.** Helios proves a block only while its hash is in the newest 8,191 (about 27 hours), so the logs and transactions of older blocks are asked of the execution servers directly: `server-reads.ts` posts them to the lane's execution name, which the lane's failover answers from the servers in use, so the route, the egress rules, the hedging, the cooldowns and the masking of addresses are the light client's own and no request leaves any other way. Only `eth_getLogs` and `eth_getTransactionByHash` pass; every other method is refused before a request is made, so a state read is always the light client's and proven. What it returns is the servers' word and proves nothing; the resolver that asks (`../../og/`) says what it does with that. A 429 always cools the server it came from for at least a second, `Retry-After: 0` included, since a server that is asked again at once answers 429 again.
