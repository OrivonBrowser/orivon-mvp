# `src/shim/wasi-p2/`: a WASI 0.2 host over `orivon.*`

**What lives here.** The host a WASI 0.2 command component runs against when `spawn` starts one
([`../child-process/`](../child-process/)): `wasi:io`, `wasi:cli`, `wasi:clocks`, `wasi:random`,
`wasi:filesystem` over `orivon.fs`, and `wasi:sockets` over `orivon.net`, in the shape jco's
transpiled output takes (`imports.ts`), and the runner that enters it through `wasi:cli/run`
(`run.ts`). Every call is an `orivon.*` call the app could already make: the host translates, and
holds no authority of its own
([`ADR-0040`](../../../docs/decisions/ADR-0040-native-shaped-node-features-run-as-webassembly.md)).
Durable: no Electron API, only JSPI.

**What it depends on.** [`../../contracts/`](../../contracts/) (types), and within the shim
[`../wasi/`](../wasi/): its path operations (`path-ops.ts`), run through its asynchronous driver
with a host context of this host's own, its errno table, clocks and termination, so both hosts
resolve, refuse, retry and stop the same way; `../fs/paths.ts`; and `../bind-scope.ts`, which maps
a bind address onto a scope for the Node shim too.

**What it must never import.** `electron`, or [`../../broker/`](../../broker/): see the parent
README.

**Owner stream.** `shim`.

**How a port ships a component.** A `wasm32-wasip2` binary is a component, which a browser cannot
instantiate directly: jco transpiles it once, at the port's build, into JavaScript and core
modules, and the port ships that output under `<program>.p2/` beside the program's path. The exact
command is `run.ts`'s `transpileCommand`, which `spawn`'s refusal of a raw component prints. Its
`--async-imports` are `imports.ts`'s `ASYNC_IMPORTS`: the imports this host answers with a
promise, which the output must let suspend through JSPI. `spawn` refuses output that lowers any of
them synchronously, naming each.

**Not served:** links and file times (`orivon.fs` has neither), terminals (a program here has
none), a second `stream()` of one UDP socket, and threads, so a Rust program runs tokio on its
current-thread runtime. tokio's own name resolution (`lookup_host`, or `TcpStream::connect` given a
name) runs on its blocking pool, which needs a thread, and traps: a program resolves with
`std::net::ToSocketAddrs` and connects by address, and the broker still checks the connect against
the name (`addresses.ts`'s `ResolvedNames`). WASI 0.2's `exit` carries only success or
failure, so a program's non-zero code reaches Node as 1, unless the component calls
`exit-with-code`, which passes its code. A listen or UDP bind asks `orivon.net` for the scope its
address implies (loopback is `local`, anything else `network`), and a `network` ask the broker refuses as `denied` is asked
again as `local`, as the `net` shim's is ([`../bind-scope.ts`](../bind-scope.ts)); a listener's
`local-address` then reports the loopback address it got. The broker binds loopback or every
interface, never one other address, so a bind to a single non-loopback address holds every
interface.

**What a file call costs.** Every filesystem import is a round trip from the program's Worker to
the page and the broker, a few milliseconds each, and the program has one thread, so it serves no
socket while it waits. A program that makes a dozen file calls per operation is slow here in a
way it is not natively. SQLite built for WASI is the common case: its default VFS there
(`unix-dotfile`) takes a lock directory and re-reads the file header on every statement. A port
whose program is the database's only user opens it with the `unix-none` VFS and
`PRAGMA locking_mode = EXCLUSIVE`; one real program's start went from 809 s to 20 s with that
change alone.

## Design notes

**jco is never one of this repository's dependencies.** It could transpile a component at run
time in the page, but its packages install native binaries (Rule 8), so the transpile is the
port's build step and the fixtures are regenerated by an opt-in test
([`tests/fixtures.test.ts`](tests/fixtures.test.ts)) that loads jco from outside the repository.

**A function with no result, such as `wasi:cli/exit`'s, must stay synchronous.** jco's glue turns
a throw from an asynchronous import into a trap it never reports, and the component hangs. A
function with a result may throw its error value either way; the glue lowers a thrown non-`Error`
as the result's error and rethrows an `Error` as a trap, which is how exit unwinds (`basics.ts`).

**A socket connects by the name the program resolved** (`addresses.ts`): a program resolves a name
and then connects to an address, while an app's grants usually name hosts. The broker is asked for
the name, checks the grant it would check for `net.connect(name)`, and resolves it itself. An
address the program did not resolve, or one that several resolved names share, goes to the broker
as it is.

**A revoked grant stops the component**, file or socket alike, as it stops a preview1 program: a
program retrying against a grant that is gone would spin. The host throws the preview1 host's
termination, which unwinds the component as a trap.

**A bind is made at listen**, since `orivon.net` binds and listens in one call: `finish-bind`
always succeeds, and an address in use is reported by `finish-listen` (`tcp.ts`). An ephemeral
(port 0) listen is confined to the app's granted range exactly like an explicit one (ADR-0034),
so a program that listens twice on a single-port grant collides with its own ephemeral listen and
sees `address-in-use` -- correct, not a bug. Listening is IPv4 in this build whatever family the
program's socket has, and a listener reports the address it bound with the port the server holds.
A UDP socket is IPv4 only: `create-udp-socket` answers `not-supported` for IPv6, as a host without
IPv6 does, so a resolver given IPv6 servers fails over to its IPv4 ones at once.

**Sockets block only where POSIX does.** A connect and a lookup are started at once and answered
`would-block` until `orivon.net` settles, and the program waits on a pollable: a non-blocking
`connect()` is `EINPROGRESS`, as a Rust or C event loop expects. A TCP listen and a UDP bind
instead suspend in `finish-listen` and `finish-bind` until it settles, because wasi-libc's
`listen()` and `bind()` take `would-block` there as failure on a non-blocking socket, which every
mio and tokio socket is; wasmtime never answers it. The streams read ahead of the program
(`io.ts`), so a non-blocking read answers from what has arrived.

**A datagram to a reserved port needs a grant naming that port.** `udp.send` is checked as
`tcp.connect` is, so a wildcard never covers a reserved port (A82), and a manifest declares a
wildcard host only as `*:*`: a program with its own DNS resolver names it, as `1.1.1.1:53`. The
broker drops a refused datagram without an error (A87), so the program sees only a query that
never gets an answer (A304).

**`poll` waits in constant time per pollable and answers a whole pass of the event loop at once.** A
program's event loop polls every socket it holds each time anything wakes it: a busy program holding
two hundred sockets polls about two thousand times a second, each call naming all of them. Three
properties of `io.ts` keep that cheap:

- *One reaction per pending wait.* A `Pollable` arms its underlying promise once, when a poll first
  watches it, and stays armed until that promise settles. Waiting on each pollable's own promise per
  call (`Promise.race`) left one reaction on the promise of every socket that stayed quiet, and a
  busy program grew its heap by about 35 MB a second.
- *A wait is a field write per pollable.* A poll that starts waiting adds one to each pollable's
  watcher count and joins one realm-wide set of waiting polls; it takes the counts back when it is
  resumed. It adds no closure and no `Set` entry per pollable, and the scan that comes first
  collects indices in one loop without an array per element.
- *One answer per pass.* When a pollable that a poll watches settles, the waiting polls are resumed
  once, at the end of the event loop's current pass (`setImmediate`, or a `MessageChannel` task
  where there is none; a timer would clamp to 4 ms in a page's Worker). Every socket that became
  readable in that pass is then in the one answer, so the program serves them all in one turn
  instead of paying the scan for each. A pollable that is ready when `poll` is called answers at once.

The glue calls `[Symbol.dispose]` when a program drops a pollable: it then wakes no poll, and a clock
pollable clears its timer, where the program drops one per `poll` call and every one would otherwise
stay scheduled to its deadline.

**A dropped socket gives back what it held in the broker, whatever it had got to.** A program that drops a socket
is closing a descriptor, and the origin's census must show it gone. One still connecting is abandoned with the
`signal` the host passes to `orivon.net.connect`, so the dial stops and its slot among the origin's in-flight calls is free
at once. One that connected has its handle closed; one that never wrote is closed at once. One that wrote is closed
through its writable stream first and its handle only after the peer has ended its side or `dropGraceMs` (five
seconds) has passed: a handle close travels the control channel, which can outrun a write still crossing the stream's
port and drop it (`tests/tcp-dispose-race.test.ts`), and the Worker cannot see a write land, since a transferred
stream settles when a chunk is posted. The grace is also what frees a socket whose peer never ends its side, which
would otherwise hold the slot for ever (`tests/socket-release.test.ts`, against the real broker). A call that answers
after the Worker is gone is closed by the page's server, not kept (`../worker/orivon-server.ts`).
