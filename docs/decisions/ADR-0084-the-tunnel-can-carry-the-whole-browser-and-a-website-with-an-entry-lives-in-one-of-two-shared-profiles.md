# ADR-0084: The tunnel can carry the whole browser, and a website with an entry lives in one of two shared profiles

- **Status:** accepted. Supersedes the storage decision of [`ADR-0082`](ADR-0082-a-websites-tunnel-state-is-kept-per-origin-and-a-website-that-differs-from-the-default-has-storage-of-its-own.md) (one session per website); the rest of ADR-0082 (a tunnel state per origin, the notice, the controls through one seam, the session held shut until it is pointed) stands. *Provisional* on the extension pieces listed under Consequences, settled by the owner's first use. The paragraph on the local IPFS and Swarm nodes (not run while the setting is on) is superseded by [`ADR-0086`](ADR-0086-the-local-nodes-run-through-the-tunnel-while-the-whole-browser-does.md).
- **Date:** 2026-10-13
- **Type:** architecture / security
- **Decided by:** owner (the whole-browser setting, `d-0619`; the two profiles, in the owner's words: extensions must run for tunnelled sites without "an entire new browser instance for extensions for each tunneled app"); AI recommendation accepted by default for the shape

## Decision

**A browser-wide default.** The setting `network.tunnel.everywhere` (*Send all of Orivon's traffic through the tunnel*, off by default) is the state an origin with no entry of its own follows. An entry (`on` or `off`) still overrides it, for an installed app on its card and for a website from its popover or Settings. With the setting on, nothing Orivon sends leaves this computer except through the tunnel, bar loopback, the tunnel's own way in (the connection to the person's SOCKS5 address), and the origins set to off.

**Where a website lives depends on its own entry alone, never on the default.**

- A website with an `on` entry lives in the tunnel profile, `persist:tunnel-profile`: one persistent session for every such website, always tunnelled, with one front and one tunnel identity, the WebRTC policy on every web contents, and the person's extensions loaded once.
- A website with an `off` entry lives in the direct profile, `persist:direct-profile`: one persistent session for every such website, never pointed at a front, with the extensions loaded once while one of its websites is open (below), as the tunnel profile's are. It is what the person gets for a site they leave out while the whole browser is on the tunnel; with the setting off an `off` entry changes nothing about the route, and the site stays in this profile so that turning the setting on later moves no login.
- A website with no entry stays in the default session, which follows the setting: pointed at the shared front while the setting is on, on the system's proxy while it is off. Turning the setting over repoints that session and reloads its web pages, and moves no website between sessions.
- An origin that may not be written to disk (plain http) gets the same profile in a session kept in memory (`tunnel-profile-memory`, `direct-profile-memory`); Electron loads no extension in such a session.
- An installed app keeps its own `persist:app-<hash>` session, with no extension, and its own tunnel identity. With the setting on, an app with no entry is on, one with an `off` entry is on the system's proxy.

**The shared identity.** The default session, and every other session the runtime creates that no origin claims (the shell's own, a local file's), take the shared front: a session is stopped when it is made, on the dead end (a listener on a random loopback port that Orivon holds, which accepts and closes, so no other program on this computer is shown a destination name), and then pointed at it. A session that sets a proxy of its own, as a web context does with its discard port, marks itself and is left alone. The requests made with no session (the verifier host's, the runtime's own) are pointed at the same front with `app.setProxy`.

**Switching on stops before it points, and the route starts ahead of the extensions.** The sessions of the shared identity, and the requests made with no session, are stopped in the very turn the setting flips on; the verifier host and the local nodes stop at once; the front is pointed at afterwards, and Orivon's own requests wait for that, a bounded time, and are refused when it does not come. At start the route subsystem runs before the extensions subsystem and settles before it returns, so the default session is pointed before the first extension loads into it.

**Every session guards its main frame** (those that register through the shared request owner; the embed, internal-page and web-context sessions answer their own requests). A main-frame load is cancelled in a session it does not belong in and that the shell did not move: a website with a profile in the shared session, and a routed website in a session that is not tunnelled. The shell moves a page before its first request commits when its session would send the address differently from the one it belongs in; a popup is not kept in its opener's session in that case. A frame of an `on` website inside a page of another session follows that page's session, by design.

**A settings file that cannot be used counts as the setting being on.** The choice about the tunnel is not known then, so the whole browser goes through it, with Nym as the tunnel, until the person turns it off; Settings says why.

**The questions T20 asks.** Whether a system proxy applies to a destination is asked of a session that only ever follows the system, never of the default session, which is the tunnel's while the setting is on: an unrouted app (one set to off) is therefore refused only when the person's system really has a proxy.

**Orivon's own requests** (self-update, telemetry, the bug report, search suggestions, an app's manifest read before install, the loader's bundle fetch) go through the tunnel or do not happen, made with `net.request` in the default session because `net.fetch` raises no `login` event for a request without web contents and so cannot sign in to the front. Lookups about a website set to off (its tab icon, its Web3 Score) go on the system's proxy. The verifier host fetches with `net.request` too, resolves no name here, and restarts when the setting flips so that its direct routes (T31, T40) stand down.

**Nym as the tunnel ([`ADR-0083`](ADR-0083-nym-is-the-built-in-tunnel-and-runs-in-a-utility-process-of-its-own.md)).** The Nym host's own connections to Nym's gateways stay direct: they are the tunnel's way out, made with Node sockets in its own process, which Chromium's proxy never reaches. The check that stops that host while a proxy applies asks the system's proxy, not the tunnel's front on the default session, or Nym could never start with the setting on. The first request through Nym waits for the host to start (up to 30 s); nothing at start-up waits on it, because the update check and telemetry run unawaited and the first window loads pages Orivon serves itself.

**The local IPFS and Swarm nodes do not run while the setting is on.** They dial their peers by address and look names up with datagrams of their own, which a SOCKS5 tunnel does not carry reliably; the controller refuses them with that reason, and IPFS is read through gateways over the tunnel.

**A Web3 name or address of a website in the tunnel profile is read through the tunnel, with the whole browser off it or on it.** The verifier host serves two sets of protocols side by side. A request from a session of the tunnel profile carries a mark that main sets on every request of that session and strips from every other (`x-orivon-route`), so a page cannot name a route for itself and a request without the mark is a direct website's. A marked request is served from a set whose every fetch is the host's routed fetch: HTTP over TLS over a `CONNECT` to the tunnel profile's front, which opens the stream through the tunnel's route with the name unresolved and signs in with the profile's credentials (main sends them in the host's start message, as it sends the shared front's). That covers IPFS blocks and IPNS records from gateways, DNSLink through DNS-over-HTTPS, name-service hosts, and CCIP-Read, whose own fence stays and which resolves no name here. The name is proved by a second Helios light client, started at the first tunnel-profile `.eth` name, whose RPC and consensus requests ride the routed fetch: Helios reaches the network only through the process's global `fetch`, so each client is given names that resolve nowhere for its two servers and a dispatcher maps a request back to the real server and to that client's own fetch. The local IPFS node is not used for such a website, and the shared block cache is not shared with it, so neither lets a request leave another way. A Swarm address or a `.eth` name that points at Swarm content is refused with a sentence saying the Swarm node cannot carry one site through the tunnel, since the node dials its peers itself and is not routed per site. With the tunnel down every fetch fails and none falls back. The app manifest read on a first visit and the loader's reads for such a website are made in the profile's session too. What stays outside the tunnel is the shared light client's own sync, which names no website and runs whenever the host does.

**Migration.** The first start after this build clears the sessions websites had of their own (`persist:site-<sha256(origin)>`) and records it; a website that has an entry lives in its profile from then on, and the person signs in to it again once.

## Context

ADR-0082 gave each website its own session, which meant a hundred tunnelled websites cost a hundred sessions and, for the person's extensions, a hundred copies of each extension. The owner asked for the shape of a profile instead: one session for the websites that share a tunnel setting, so that extensions load once. The cost is the isolation ADR-0082 kept: every website in the tunnel profile shares one tunnel identity (Chromium picks a proxy per session), so a tunnel that isolates by identity (Tor's circuits) correlates them. Installed apps keep their own identities. The owner accepted the trade.

## Alternatives considered

- **Send the verifier host's requests to the tunnel's SOCKS5 address.** Not done: the Nym host's port changes at each start and Nym is started on demand, so the host would have to ask main for the address at each connection; the profile's front already does that, waits for Nym, follows a changed tunnel and fails closed.
- **One light client for every website, with the tunnel chosen per request.** Not done: Helios runs its RPC from a WebAssembly executor through a global `fetch` and gives a request no way to name the website that caused it, so a per-call route would be a guess; two clients are the reliable shape.
- **Open a Swarm site through the local node anyway.** Rejected: the node dials peers directly, which is exactly what the tunnel is meant to prevent for that site.
- **One session per website, as ADR-0082.** Rejected for the memory and extension cost above.
- **One profile for everything the default does not cover, with the proxy chosen per request.** Rejected: Chromium sets a proxy per session, and a request-time choice would put an `off` site's storage next to a tunnelled site's.
- **Move the websites with an `off` entry into the default session while the setting is off.** Rejected: a site's login would then move when the person flips the setting, which the owner ruled out.
- **Route the local nodes through the SOCKS5 provider.** Not done: the nodes resolve names with UDP and dial peers by address, which neither SOCKS5 UDP ASSOCIATE nor a name-based `CONNECT` carries for a peer-to-peer protocol; refusing them with a reason is the honest answer until a node can work over a tunnel.
- **Extensions in the profiles through the one library instance of the default session.** Not possible: an instance serves one session. Each profile session has an instance of its own instead.
- **Keeping an extension's settings the same in every profile.** Not done: it would copy the extension's storage between sessions and follow every change in both directions, and uBlock Origin's storage has grown without bound before.
- **The direct profile's extensions running whenever the direct profile exists.** Rejected: with the whole browser on the tunnel an extension's own requests (list updates, telemetry) would leave directly while no excluded website is open.

## Reasoning

The two profiles are the smallest number of sessions that keep a tunnelled and a direct website apart and give each their storage. Following the website's own entry alone keeps a person signed in however they flip the default. Asking the system's proxy of a session that only follows the system keeps T20 meaning what it says. Making Orivon's own requests with `net.request` is the only way a main or utility process can sign in to the front, which Step 0 measured on Electron 44 (`net.fetch` in a utility process ends at the front's `407`; `net.request` with a `login` listener passes).

## Consequences

- Every website in the tunnel profile shares one tunnel identity; the threat row says so.
- The extensions run in a profile as they do in the default session: one copy of each per profile, with a library instance of the session's own, so the toolbar button and popup, `chrome.tabs` and `chrome.windows`, rules added at run time and a blocker that works through the webRequest API (uBlock Origin among them) act on the pages of that session. The toolbar follows the session of the tab in front. Each copy has storage of its own, so a profile keeps its own settings for an extension (uBlock Origin's filter lists and whitelist among them); keeping them in step would copy an extension's storage between sessions, which Orivon does not do. The copies share what is the process's: the rules an extension adds at run time (one engine, keyed by extension id), and the history, bookmarks and top sites an extension with those permissions reads. A profile has no side panel and no keyboard shortcuts of extension commands, and a website in a profile that is plain http runs no extension.
- **A profile's copies run only while one of its websites is open.** Opening the first loads them and closing the last removes them, in the direct profile and in the tunnel profile alike, so with the whole browser on the tunnel an extension makes no direct request while no website the person left out is open, and an idle profile holds no extension memory. The cost is one copy of each extension per profile in use; its measure is in the decision log. Keeping the tunnel profile's copies once loaded was rejected: everything they send goes through the tunnel, but each active profile holds about 100 to 400 MB of them for nothing while it has no site.
- Moving a website into or out of a profile reloads it and signs the person in again once.
- The IPFS and Swarm nodes are off while the setting is on.
- The decision-log row records the migration; the sessions the earlier build made are cleared once.

## Reversibility

- **Cost to reverse:** moderate. The profile names are a stored layout: moving back to a session per website signs the person out of each once more.
- **What would make us revisit:** a browser-level extension host that reaches more than one session (the extension limits end); a local node that can work over a tunnel; or the owner's first use showing that one identity per profile is too coarse for Tor.
