# ADR-0075: A published app is let in as soon as it is allowed, and each file is checked as it is served

- **Status:** accepted. Supersedes [`ADR-0074`](ADR-0074-a-published-app-is-asked-about-and-checked-before-its-page-is-entered.md)'s D2 to D4 (the download and check before entry, and the retry sheet that download needed); D1 and D5 stand. Amends [`ADR-0018`](ADR-0018-isolation-follows-consent.md) (a consented app's tab is in its own partition from its first entry, served from the verifier until its pin lands) and [`ADR-0029`](ADR-0029-sites-publish-their-bundle-hash-tree.md) (the declared tree is checked per file, as the file arrives).
- **Date:** 2026-10-09
- **Type:** architecture / security
- **Decided by:** owner (the correction below); the choices under How it is done are implementation calls, provisional where they say so

## Decision

The owner, on the merged flow: "With the change you made previously you make load the entire app before opening it. What I asked for was different, I asked, open the app as quick as you can, ask the grants as quick as you can, and if while the pages are loading bad data arrives, the loading of such data is blocked."

A first visit to an app Orivon has never held now runs in this order:

1. **The person is asked as soon as the manifest is read** (ADR-0074 D1, unchanged), and the app's declared tree (`/.well-known/orivon-ddoc.json`) is read in parallel with the question, so it is ready when the person answers.
2. **Allow grants at once and the tab enters the app at once** (app tab, Node globals, its own isolation). The app's files are loaded on demand, like any site's.
3. **Every file the page loads is checked as it is served** against the leaf the declared tree gives it (`leaves: { "/path": "sha256:..." }`, the loader's own leaf function, so the leaves are those `orivon-port hash` prints). A file is delivered only after its leaf matches. A mismatch against the version being served is bad data, unless the app's current tree names the bytes (item 5): that response is never delivered, the tab is stopped and covered by the security warning (no way forward), every grant of the origin is removed and the app is forgotten. A bad first document is never seen.
4. **The whole bundle is downloaded and pinned in the background**, after entry. A later visit is served from the pin. A background download that fails is silent and finished on the next visit; one that fails an integrity check (a file differing from the declared tree, or content the verifier proves is not what its address names) is bad data, the same block, even though the page loaded fine.
5. **"Allowed, not yet pinned" is a durable state, and it follows its URL.** The manifest that was allowed, the root it was read from and the tree the site declared are kept on disk until the pin lands. After a restart, or a download that did not finish, the app is served again as it was allowed, every file checked, its grants as saved, and its pin resumes when it is used. It never takes the ordinary install path, which does not check. **A new version is not bad data.** Bad data is a file whose bytes do not match the declaration of the version being served. When the name leads to another root than the one allowed, or a file differs from the allowed tree, Orivon reads the app's current manifest and tree (the name's current root, or the site's host): bytes that match the current tree are a new version, and the live check, the kept consent and the background pin follow it. Grants attach to the URL (ADR-0056's "ask before moving" is for an app already served from its pin, which has a version to keep running); if the new manifest declares capabilities beyond the grants held, the existing install question asks for those, beside the running app, and otherwise nothing is asked. No warning, nothing is forgotten, no storage is touched.
6. **An app that publishes no declared tree** (a 4xx, or a body that is no tree) is let in on Orivon's own checks alone: the manifest's file list, the byte caps, the entry check. That is weaker, and a site that wants the per-file check publishes its tree.
7. **Unchanged:** the first navigation is held until the question is answered (verifier-served origins), Deny opens a plain website and only a pressed Deny is remembered, Escape and timeouts record nothing, Settings "Ask again", the gateway retries, revocation on a block, and the hint path for `https` (blank before asking).

## How it is done

- **Where the check runs, for an app a verifier serves.** Origins the verifier serves (`<cid>.ipfs.orivon`, `<key>.ipns.orivon`, `.eth`) are served by Orivon's own loopback server, which already holds each file's bytes. A request that names the leaf it expects (`x-orivon-expect-leaf`) gets its file only after the server buffered that one file, verified it against its address as it always does, and hashed it to that leaf under the request's canonical path; on a mismatch it answers `502` with `x-orivon-failure: ddoc-mismatch` and no byte of the file. A range is cut from the buffered file after the check. Bytes are held against the app's own origin and taken as they arrive, so one large cold file does not starve the scripts beside it into `503`s.
- **Where it runs, for an app on an ordinary https site.** There is no server of Orivon's between such a page and its host, so the live handler is the check: it fetches each file of the app's origin itself, from main, never through the handler (the loader's own fetch, with its public-address guard and same-origin redirects, no cookies), holds it whole, hashes it with the same leaf function and delivers those bytes. The page runs exactly the bytes that were checked; a host cannot show a check honest files and the page other code. It believes no header such a host sends.
- **The expected leaf comes with the request, not from state in the verifier.** The leaf table lives in the shell, beside the registration that makes the origin an app; the server keeps nothing to replay when the host restarts or sleeps. Every request names the root the manifest was read from, so a name that moved fails rather than mixing two releases.
- **The consented app has a partition before it has a pin.** A tab's partition is fixed when its view is built and an origin's partition needs a handler for its scheme (ADR-0007), so the app is registered with a handler that answers from the verifier or the host (`src/loader/serve/live-serve.ts`) and the tab enters its own partition at once, whatever the origin. That handler resolves a request against the files the manifest lists, as the pinned handler does, applies the same CSP, isolation headers and third-party reach gate, and answers a file only once its leaf matched. `registerServingFor` replaces it in place when the pin lands. `isOriginServedFromCacheSync` keeps its name and now means "has a handler of its own partition"; `isOriginPinnedSync` says it answers from the pin, and is what the trust indicator and the verifier's idle test read.
- **What is bad data and what is only a failed load.** A listed file the declared tree has no leaf for, a leaf that differs, bytes past what an app may carry, and the manifest itself differing from its leaf, are bad data. Content the verifier proves is not what its address names is bad data. A gateway that lied while no honest one held the block carries no such header, and a host that is unwell answers 5xx: both are a failed load of that file, a network error to the page, with nothing forgotten and no warning. A path the manifest does not list is answered `404` and is not bad data: a page can reach what a pinned app could and nothing more, and a probe for an unlisted path must not block an app. *Provisional.*
- **The block** is one function (`src/main/install/first-visit-keeper.ts`, `createKeeper`), raised once however many files fail. Every page of the origin goes first: each tab is stopped and emptied, whatever its `beforeunload` says, every other page of the app's partition (a popup, a context's host) is closed (`src/main/app-setup/block-tabs.ts`). Only then do `Broker.forgetOrigin` revoke every grant, every pick and the handles they opened and delete the registration and version floor, and the consent record goes. **The person's data stays:** a block takes an app's permissions, never what it stored in its own partition (local storage, cookies, databases). The partition keeps a handler that refuses everything, and the origin is no app of this run, so its next visit is a first visit that asks again. The tabs are covered with the warning meanwhile. A block is not remembered.
- **The tree cannot be read** (a 5xx, a timeout, a dropped connection) is the one wait left after Allow: a "Couldn't check" sheet with Try again, nothing granted, the answer kept. It is no permission to skip the check.
- **The background download holds the origin's queue** and the origin reads as `settling`, so a page's own manifest hint does not start a second install beside it. It begins three seconds after entry so the first page has the connection to itself, and, for an app served again after a restart, when it is first used.
- **A new version is noticed** by the verifier answering that the root asked for is no longer the one the name serves, by a file that is not the one the allowed tree names, or by the background download finding either (a 409, a manifest that changed under it, whole files that match their own tree but not the allowed one). A new manifest its own tree contradicts, or a tree that cannot be read, is no version to follow: the file stays bad data, or a failed load.

## Not verified by reading

- **A service worker** in an app's partition is routed through the handler: `e2e-first-visit-service-worker` registers a worker whose script differs from the declared tree and one whose own fetch does, and each is a block. The HTTP cache of Chromium could in principle answer a request around the handler; for a scheme a `protocol.handle` serves no spec shows it does, and the handler sends no validators or lifetimes for a cache to keep. What a document's memory cache reuses within a page is bytes that were checked when they arrived.

## Alternatives considered

- **Download and check the whole bundle before entering** (ADR-0074 D2). Rejected by the owner: the person waits for the app before it opens.
- **Push each origin's leaf table into the verifier host.** Rejected: it is state that dies with the host's restarts and sleeps and must be replayed, for no check the request header does not already make.
- **Enter in the shared session until the pin lands.** Rejected: whatever the app stores in its first minutes would be left behind when the tab moves to its own partition.
- **Let the page load straight from the verifier in a partition with no handler.** Rejected: no reach gate and no CSP for the app's requests.
- **Check an https app's bundle in the background only.** Rejected: that check is a separate cookie-less fetch, so a host could answer it with honest files and the page with other code; the page must run the bytes that were checked.
- **Block, or forget the app, when the name moves or the site is deployed before the pin lands.** Rejected: that is how every published app updates, and an update must never look like tampering or cost a person their data.
- **Serve an allowed, not yet pinned app on the ordinary install path after a restart.** Rejected: that path checks nothing per file and can move to a new release unasked.
- **Block only the file and let the page run on.** Rejected: bad data arrives from a publisher whose other files are then suspect, and the owner's answer is that the origin loses every grant.

## Consequences

- Between Allow and the pin, every file of an app passes through the shell once more than a pinned app's would, and an app on an ordinary site is fetched by main, not by the page. A failed background download leaves the app registered and granted, remembered, and served again checked on the next visit, which resumes the pin.
- A deploy or a republished name is followed, never blocked, as long as the new files match the new tree. A site that publishes no tree is bound to nothing.
- A first page an https app loaded in the default session before the question (the hint path) is replaced by an empty one before anything is asked, as before; nothing of it is kept.
- The verifier host stays awake while an app served from it has a tab, as a site does.

## Reversibility

- **Cost to reverse:** moderate. The check is one request header and one function in the loopback server; the live handler is one file the pin's handler replaces; the order is one function.
- **What would make us revisit:** apps whose files are large enough that buffering one to check it is felt (the cap is 64 MiB), a measured gap between the live handler's responses and a pinned app's.
