# ADR-0102: Verified Swarm chunks are kept on disk per site, in the verifier host

- **Status:** accepted. Extends [`ADR-0077`](ADR-0077-swarm-content-is-verified-chunk-by-chunk-from-a-local-node.md): its rule that a chunk is used only after its address is recomputed now also covers a chunk read back from disk. **Amended 2026-10-29 (`d-0748`)**: a mount no longer waits for the Swarm node before it reads from disk; a read waits for the node only where a chunk has to come from it. **Amended 2026-10-29 (`d-0749`)**: the hash of a chunk read from disk, of a leaf of a bulk read and of a single chunk is made on a few worker threads of the host, not on its one thread. **Amended 2026-10-29 (`d-0750`)**: the update a feed was last followed to is kept too.
- **Date:** 2026-10-28
- **Type:** architecture / security
- **Decided by:** AI recommendation accepted by default

## Decision

The verifier host keeps the content-addressed chunks of Swarm that it has verified in one SQLite database, `<profile>/verifier/swarm-chunks-<id>.db`, opened with `node:sqlite` (`DatabaseSync`, part of Electron 44's Node: no native module). `<id>` is the first 16 hex characters of sha256 of the profile's partition salt, the salt the IPFS node's store is keyed by. A row is keyed by the partition key (`partitionStoreKey(salt, partition)`, base64url of sha256 of the salt and the site's origin) and the chunk address, so no origin is in the file in plain text and one site's chunks are never another's hits. A site read through a tunnel (Nym or the person's SOCKS5 proxy) is kept under its tunnel's name as well, as the in-memory caches of the routes are kept apart: what the direct profile fetched never answers a tunnel's page, and the reverse.

- **What is kept.** The content-addressed chunks, the ones `ChunkSource.get` and `ChunkSource.leaves` fetch, and, apart from them, the one single-owner chunk of the update each feed was last followed to ([`ADR-0103`](ADR-0103-a-swarm-feed-site-opens-from-the-update-it-last-followed.md)). No other single-owner chunk is kept.
- **Trust.** A row read back is hashed against its address (`verifyCac`) before it is used, as a network answer is, and the check is the same one wherever it runs: on one of at most three worker threads of the host (`max(1, min(3, cores - 1))`, started when a check first waits and ended after 30 s with none), or in the host's own thread where no thread can run it. A thread must first answer a known genuine chunk and an altered one correctly, and its "not genuine" is checked again in the host before a row is dropped. A row that fails is deleted and the chunk fetched again. The disk is trusted no more than the node. A kept feed update is the exception: it is a single-owner chunk, checked by `verifySoc` in the host's own thread each time it is used, and a read of its address as an ordinary chunk leaves it in place.
- **Size.** At most 256 MB of chunk bytes in all, shared by every site; the file on disk is about a sixth larger (32 KB pages hold seven 4 KB rows each, and two indexes), and its `-wal` is cut back to 8 MB after each checkpoint (`journal_size_limit`), so a full store takes about 300 MB of the person's disk, plus a `-wal` of 8 to 33 MB. The cap counts chunk bytes, not file size, as the IPFS node's store does; lowering it to make the file 256 MB would shrink what a revisit can find by a sixth for the sake of a figure. When a write passes the cap, rows go least recently used first, down to nine tenths of it. Use is a count the file keeps itself, which goes up by one for each minute of use and once at the start of a run, so a clock that is wrong or moves back cannot make old rows look new. It lives in its own table beside the chunk rows, together with each row's size, and a row is marked at most once a minute, from a read of the file and from a read the memory in front answered, so marking never rewrites a 4 KB row.
- **Memory in front.** `KeptChunkMemory` is a `BlockMemory`: `recall` asks the in-memory `BlockCache` alone, so it never waits; `recallKept`, an optional member of `BlockMemory` for a slower store behind the cache, asks the database, and a chunk it took from the disk is then answered from memory; `remember` writes to both; `share` stays the in-memory one. `recallKept` reads one row at a time from SQLite, each after a turn of the event loop of its own, and hands the row to the checker without waiting for its answer, so the next row is read while earlier ones are checked, and `ChunkSource.get` and `ChunkSource.leaves` call it after `recall` missed: `leaves` looks up every leaf of a file that way first, then fetches the leaves neither held in one `/bytes` request, as before. A mount with no partition keeps nothing, as before.
- **Writes.** WAL journal, `synchronous = OFF`, 32 KB pages (a chunk row is a little over 4 KB, so a smaller page would give each row two). Rows wait and go in one transaction when 64 are waiting or 250 ms after the first, so a file of 2,000 chunks is about thirty commits. A failed write is logged once and drops that batch; no load fails because of the store.
- **Why `OFF` is safe here.** With `NORMAL`, the commit that crosses SQLite's auto-checkpoint (1000 pages, 32 MB) runs the checkpoint and its `fsync` inside the host's own `flush()`: measured on 256 MB of chunks, 470 to 600 ms every 25 to 35 flushes and 1.9 s at worst, during which no protocol the host serves answers. With `OFF` the same writes took 1.4 ms at the median and 6 ms at the worst. `OFF` leaves a file at risk only of a crash of the computer (a crash of the process loses nothing a commit reached), and nothing the file holds has to survive that: every row is hashed against its address when it is read, so a torn page costs a download; the bytes kept and the use count are worked out from the rows when the file opens, never read from a figure the last run wrote; and a file SQLite reports as damaged is deleted and made again. Lowering `wal_autocheckpoint` with `NORMAL` was measured worse (more checkpoints, each with its `fsync`), and turning auto-checkpoint off lets the `-wal` grow without a bound.
- **Counting.** At open, the bytes kept are the sum of the sizes in the `age` table and the use count is its newest mark. Summing the chunk rows themselves reads the whole file: 41 ms with it in the system's cache and 52 to 119 ms without (two runs), for 256 MB, on the host's event loop, and more on a slow disk; the `age` table is a few dozen pages and took 2.5 ms.
- **Opening.** At the first use, which is the first Swarm mount with a partition. A new file gets its tables and `PRAGMA user_version` in one transaction. A file SQLite reports as damaged, when it opens or later in use, and a file whose `user_version` is not this code's (a layout it does not know) is deleted and made again, once in a run; the second time the host keeps chunks in memory for the rest of the run. The file is a cache, so a layout this code does not know is remade, never read, and never kept as it is for the person to deal with. A file that fails any other way (a full or locked disk) is left as it is, with one line logged, and chunks stay in memory. The host is given a salt and a directory only when the profile can hold them, so a profile that cannot be written starts a host without the store.
- **Forgetting.** Clearing cached data or all history stops the IPFS node, replaces the salt, puts the host to sleep and waits for its process to exit (at most 10 s), then deletes every `swarm-chunks-*` file except the one of the salt in force at that moment (a second clear, or a host started meanwhile, may have made it newer), with its `-wal`, `-shm` and `-journal`. Every file is tried before a failure is reported, so a locked one does not keep the rest. The host deletes every `swarm-chunks-*` file whose id is not its own salt's as it starts (when its `SwarmChunkDatabase` is made, before anything is opened), so a file main could not delete (Windows keeps an open file) goes at the next start. When the salt itself cannot be replaced, the host is still put to sleep and every `swarm-chunks-*` file goes, the file of the salt still in force too, so nothing keeps answering from what the person asked to forget; the failure is reported after.
- **Report.** The host's log line for a mount, and for a file of 256 KB or more, says how many chunks that mount or that read took from disk, whatever else was being read; the store logs its size when it opens. No line names an address or a site.

## Context

Swarm sites load from Orivon's own Swarm node, which runs with `--no-disk-cache` because its disk cache needs threads WASI lacks. Orivon kept verified chunks only in memory (64 MB, in the verifier host), so after a restart, or after the host slept, a revisit downloaded everything again: the WebTorrent app's page took 15 to 19 s every time. The IPFS node keeps a 256 MB `blocks.db` keyed by the same salted partition, so an IPFS revisit is local.

## Alternatives considered

- **A disk cache in the Swarm node.** Not possible: the node's cache needs threads, which its WASI host does not give; the reason it runs without one.
- **The store in the main process.** Rejected: the host is where chunks are verified and where `ChunkSource` runs, and `BlockMemory.recall` is synchronous, so a round trip to main would turn a lookup into a message. The host is an unsandboxed utility process, so a directory it writes opens no capability it lacked; it does write one directory of the profile now.
- **One file per site.** Rejected: a site opened once leaves a file, there is no single place to count the cap, and a file name that is a function of the origin shows the sites visited.
- **Files on disk, one per chunk.** Rejected: 60,000 small files for a full cache, a directory listing to find the least recently used, and no transaction.
- **A key without the salt (the chunk address alone).** Rejected: a site could then tell, by how fast a chunk loads, whether another site fetched it, which is the leak the in-memory cache already closes (A256).
- **Keeping single-owner chunks and feed updates.** Rejected as the answer to a feed, because a kept update is a stale answer to the question the feed exists to ask. [`ADR-0103`](ADR-0103-a-swarm-feed-site-opens-from-the-update-it-last-followed.md) keeps the last update a feed was followed to anyway, opens from it, and asks for a newer one in the background.
- **Compressing rows.** Not taken: chunks of media and archives do not compress, and the cost lands on the read path.
- **Hashing in the host's own thread, one chunk to a turn.** Not taken: it spreads the hold over many short turns, but a file of two thousand chunks still costs the host the whole hash, and a protocol it serves waits behind each turn's share of it.
- **A built file for the thread beside `verifier-host.js`.** Not taken: Electron 44's utility process does start a thread from a file inside `app.asar`, but a file is one more output to build, name and keep in the package, where a string travels inside the bundle the package already checks.

## Reasoning

Verification does not change: every byte used is in a chunk whose address was recomputed from it, on the way in from the node and again on the way out of the file. What the file adds is availability, so the worst a corrupt or replaced file can do is cost the download it was meant to save. Keying by the salted partition keeps the IPFS store's property: the file holds no origin, a copy of it means nothing in another profile, and one site's chunks answer only that site.

## Consequences

- A Swarm site seen before opens from disk: no request to the node for a chunk the site has already read, up to the cap.
- The file is larger than the bytes it counts, by about a sixth, for page padding and the indexes, and its `-wal` adds 8 MB to 33 MB (it grows to 32 MB between checkpoints and is cut back to 8 MB after one): a full store takes about 300 to 335 MB of disk for the 256 MB it counts.
- A chunk taken from disk is hashed on a worker thread (about 0.7 ms for 4 KB), while the host's own thread reads the next row. A file of two thousand chunks read entirely from disk no longer holds the host for its whole hash, so IPFS and ENS answers are not kept waiting behind it. A thread that cannot start, dies, answers wrongly or goes 5 s without answering ends the pool for the run; every check waiting is then made in the host's thread, one to a turn of the event loop, and one log line says why. The thread is a self-contained script held as a string and started with `new Worker(code, { eval: true })`, so it needs no file inside `app.asar` and no unpacked copy. The pool lives in `src/protocols/verifier-host/` and imports no Electron; `src/protocols/swarm/` sees only a `ChunkChecker` interface.
- The host now writes one directory of the profile (`verifier/`), where it wrote nothing before.
- The salt that keys the IPFS node's store also keys this one, so clearing cached data forgets both, and a profile with the IPFS node off still has a salt.
- Whoever holds the whole profile directory has the salt beside the file: the keying defends against timing between sites and against origins in plain text in the file, not against that reader.

## Reversibility

- **Cost to reverse:** cheap: the gatherer takes its memory as an option, and removing `config.swarmChunks` returns to memory alone; the files are a cache.
- **What would make us revisit:** a Swarm node whose own disk cache works under WASI (the store would then duplicate it), or `node:sqlite` leaving Electron's Node.
