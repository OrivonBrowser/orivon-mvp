## Blockers — technical, verified against live sources

### B1. MKV has no playback path in v0 — APPLIED
MSE accepts only WebM / fMP4 / MPEG-TS (W3C byte-stream registry; Matroska absent). Chromium's
`<video>` cannot demux MKV either, so falling back to an HTTP server does **not** rescue it —
both paths die at the same demuxer. `subprocess` is excluded from v0, closing the VLC handoff
that `webtorrent-desktop` relies on. Most torrented video is MKV.

**Owner decision:** ship MP4/H.264 only in v0, state the limitation in-product, shoot the clip
against an MP4 torrent. Remuxing (`libav-wasm`, pure-WASM so the dependency rule holds) is the
first post-launch item, not month-1 scope.

Verified good news: stock Electron ships `proprietary_codecs = true` / `ffmpeg_branding =
"Chrome"`, so H.264/AAC works out of the box. HEVC has hardware decode only (Linux: VAAPI
only), with no software fallback — another reason v0 is H.264.

### B2. `webtorrent` in a renderer resolves to the WebRTC-only build — APPLIED to the spike
Its `package.json` `browser` field maps `net`, `bittorrent-dht`, `ut_pex`, `load-ip-set`,
`./lib/utp.cjs`, `./lib/conn-pool.js` → `false`. Bundling with default resolution silently
produces **Brave parity** — and `ADR-0001` reason 3 rests entirely on beating exactly that
("Brave has shipped WebTorrent since 2018, but only over the WebRTC swarm").

Working config needs per-module resolution overrides: Node resolution for
`net`/`dgram`/`bittorrent-dht`/`utp`/`conn-pool` (aliased to the shim), browser resolution for
`webrtc-polyfill`. Nothing about this is the mechanical shim the docs assumed.

### B3. `node-datachannel` is a hard native dependency — APPLIED
Verified by real install: `webtorrent → @thaunknown/simple-peer → webrtc-polyfill →
node-datachannel@0.32.3`, non-optional at every link, **CMake + libdatachannel**, not plain
node-gyp. Fallback build needs a C++ toolchain — strictly worse than the Visual Studio Build
Tools case the platform policy already rejects. Also present: `utp-native`, `bufferutil`,
`utf-8-validate`, `fs-native-extensions` (optional, but npm installs optionals by default).

**Fix adopted:** ship webtorrent as a **pre-built app asset** rather than a shell dependency.
The shell's `npm install` never sees it. This makes `ADR-0005` a portability win it did not
previously claim.

## Thesis-level findings

### TH1. `fetch()` bypasses the broker, inverting the trust indicator — APPLIED
App renderers keep ordinary web capabilities, so an app can reach any host via `fetch()`,
`WebSocket` or WebRTC invisibly. An app doing all networking to its own central server shows
**zero** broker-observed connections and therefore scores as maximally local. The feature built
to detect dishonesty awards its best grade to the dishonest case. Grep confirmed: zero mentions
of CSP, `connect-src` or webRequest filtering anywhere in the corpus.

### TH2. The connection ladder is cheaper to fake than to earn — APPLIED
An app exfiltrating `files/` by spraying it across 200 short connections to 200 attacker IPs is
classified **"swarm pattern"** — the top grade. The exfiltration *is* what earns the score.
Compounding: the log is in-memory, so the app controls when watching stops; and byte volume and
direction are not in the ladder at all.

### TH3. No journey demonstrates URL delivery — APPLIED
Journey 1 runs a **pre-cached** app, journey 2 injects into third-party sites that are not apps,
journey 3 loads an **unpacked local directory**. The entire risk budget — pulling the shim into
month 1, the spike, denying the flagship the cheap main-process path — buys a capability that no
user-visible moment shows. Journey 2 additionally proves little: `window.nostr` injection is what
nos2x and Alby already do in Chrome.

## Security findings

### S1. Origin derived per-WebContents, not per-frame — APPLIED
A `WebContents` is a *tab*; preloads re-inject on **every navigation** and run in iframes by
default. An app holding `tcp.connect *:*` navigates to `evil.com`, which now runs with the
Orivon preload while the grant ledger still resolves to the app's origin.
**This defeats the publisher-key amendment entirely** — a compromised host does not need the
signing key, it serves a 302.

### S2. The `MessagePort` is a bearer capability — APPLIED
`MessagePort` is transferable and `port.on('message')` carries **no sender identity** — which is
exactly why it is fast. An app can `postMessage` a live socket port to any origin, which then
reads and writes a raw TCP socket with no manifest and no grants. **The performant
implementation is the insecure one.** Design rule 3 ("checked once, at acquisition") is unsound
for anything transferable.

### S3. Silent-update comparison is at the wrong granularity — APPLIED
Under the A9 default (grants keyed on `(origin, capability)`), an update changing
`["api.example.com:443"]` → `["*:*"]` requests **no new capability** and installs silently.
Also missing: any version floor, so a signed *older* bundle replays silently forever.

### S4. `orivon.net` bypasses Chromium's proxy configuration — APPLIED
Node `net`/`dgram` do not honour `--proxy-server`. A Tor user watches pages load through the
proxy and reasonably concludes they are covered, while DHT and peer traffic leaves from their
real IP. Same for DNS. Found in five minutes with `tcpdump`, and reported as a leak rather than
a missing feature.

### S5. Raw signing oracle over an unbackupable cross-origin key — APPLIED
`IdentityHandle.sign(payload)` signs arbitrary bytes silently after one connect prompt. A
compromised Nostr client can wipe the follow list (kind 3), delete posts (kind 5), replace the
profile (kind 0), authenticate as the user to relays (NIP-42, kind 22242), and — if
`nip04/nip44.decrypt` is offered, which the docs never specify — read the entire DM history.
`ADR-0003` excludes export/backup, so the user cannot rotate.

### S6. Origin used literally as a filesystem path component — APPLIED
`https://Example.com` and `https://example.com` are distinct origins that map to the **same
directory** on macOS/Windows — a silent cross-app data leak on one platform only. Separately,
`code/` and `files/` are siblings, so a one-level `fs` escape reaches executable code.

### S7. Ordinary tabs *do* get a preload — APPLIED
T4's mitigation ("normal tabs get no preload") is contradicted by `window.nostr` being injected
in ordinary tabs. The real invariant — two distinct preloads — was never written down.

### S8. Telemetry timestamps are a behavioural fingerprint — APPLIED
Per-session `startedAt` against a stable ID over months is a daily activity pattern (waking
hours, working hours, real timezone) — more identifying than `country`, and unnecessary: the
metric needs a sum, not a timeline.

### Second tier, recorded, not all applied
`fs.userSelected` scope/lifetime undefined · handle tables must be per-origin · broker
saturation freezes every tab · developer-mode grants persist on loopback origins · `magnet:`
argv injection + drive-by swarm join + handler squatting · T12 precision gaps (`*` vs private
ranges, TOCTOU re-resolution, `net.listen` bind address, broadcast/multicast) · T8 overstates
`safeStorage` · `<account>.github.io` shares one origin across every repo on the account.

## Schedule and scope

- **The month is oversubscribed**, and `readiness.md` says the owner's best use of the month is
  *not* this repository while `build-plan.md` assigns four weeks of implementation. Neither
  document reconciles the two.
- **Five IN-table items have no build step**: disk-usage UI, app uninstall, settings UI with

  `events`, `crypto`, `path`, `os`, `process` and an HTTP client for trackers.
- **Spike naming is inconsistent** — "week-0" in `CLAUDE.md` and `build-plan.md`, "week-1"

**Owner decision:** cut the signing tier only. Trust indicator is fixed properly (~2 days)
rather than cut. Net effect on the month: **+1 day**, against a plan already over budget. The
schedule pressure is real and unresolved — recorded here rather than smoothed over.

## Metric

**Applied:** telemetry now splits `activeSec` (focused + interacting) from `backgroundSec`
(running, idle, seeding), and the metric is stated on `activeSec`. A seeding tab previously
satisfied 25 h/month on its own, which made the daily-use hypothesis unfalsifiable in the
direction that flatters it.

**Corrected, owner-side:** the "115–130 installs" figure divided 100 by the telemetry consent
rate and applied no retention or activation. An honest chain (download → still installed at day
7 → reaches 25 h/month) implies **1,500–10,000 downloads**. Also unstated anywhere: 25 h/month
cannot be observed until ~30 days after ship, so the metric resolves around month 3, not month
1. Distribution planning is explicitly **outside** the technical work session.
